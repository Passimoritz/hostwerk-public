# Building Hostwerk extensions

**English** · [Deutsch](README.de.md)

An extension adds a **page** (in the sidebar), a **tile** (on the overview) and/or a **service** (a program Hostwerk
starts) to [Hostwerk](https://github.com/Passimoritz/hostwerk-public). It is a folder with a `manifest.json`, plain
HTML/JavaScript and two text files – no build step, no framework required.

| Player Ticker (dark) | Player Ticker (light) |
|---|---|
| ![Player Ticker in dark mode](img/player-ticker-dark.png) | ![Player Ticker in light mode](img/player-ticker-light.png) |

Extensions **cannot break Hostwerk's design**: the SDK brings Hostwerk's design kit and passes the current colours,
light/dark mode, font and language into the page at runtime. Use the `hw-*` classes and `var(--hw-…)` colours – the
check warns about hard-coded colours and fonts.

### No extension may

Hostwerk enforces these limits technically for every sandboxed extension – all from other sources, every page in its frame and own server code in its own process. `scripts/ext-security-test.js` tests each one with a deliberately nosy test package.

- **Read passwords, vaults and secrets** – Password manager, vaults and keys are blocked; fields that look like secrets arrive blacked out in every allowed answer. <sub>(enforced in: server/services/extpolicy.js: DENY_FIRST (pw, passwords, vault, secrets), DENY_RE, redact())</sub>
- **Read Hostwerk’s settings, keys and login tokens** – Settings are blocked, the process does not inherit Hostwerk’s environment, cookies and tokens never reach the extension. <sub>(enforced in: extpolicy.js DENY_FIRST (settings, auth, tokens, keys); extsandbox.js start() env + STRIP_HEADERS)</sub>
- **Give itself more permissions** – Permissions are in the package and only apply after your consent. Its own manifest.json is read-only, Hostwerk’s extension management is blocked, "_" fields are set by Hostwerk only. <sub>(enforced in: extpolicy.js DENY_FIRST (extmarket, extstudio, ext); extsandbox.js --allow-fs-write nur Datenordner; extmarket.js installFromDir (ohne „_“-Felder))</sub>
- **Install, change, switch off or call other extensions** – Only where the other author allows it: extensions ("extend:extensions"), offered services and shared storage. <sub>(enforced in: extpolicy.js DENY_FIRST (extmarket, x); extmarket.js /call (nur eigenes /x/&lt;id&gt;); extmarket.js sharedStorage)</sub>
- **Affect Hostwerk’s maintenance, safe start or updates** – Maintenance, self-care and updates are blocked; packages that mention maintenance files or switches cannot be installed at all. <sub>(enforced in: extpolicy.js DENY_FIRST (maintenance, keeper, update, app); check.js TAMPER_RE)</sub>
- **Hide itself or make itself impossible to remove** – Every extension is listed here and in maintenance and can be switched off and removed there. It cannot clear its access log, messages always carry its name. <sub>(enforced in: check.js HIDING_KEYS (Installation abgelehnt); extpolicy.js DENY_FIRST (extmarket); extsandbox.js op toast (Name davor))</sub>
- **Read or write files outside its own folder** – The server code only reads its package and writes only into its data folder; Hostwerk’s file area is blocked. <sub>(enforced in: extsandbox.js start(): node --permission --allow-fs-read/--allow-fs-write; extpolicy.js DENY_FIRST (files, fs))</sub>
- **Send requests to addresses not named in the package** – None without the "network" permission. Server code never reaches the local or home network or 127.0.0.1. Pages may show images and media from https addresses. <sub>(enforced in: extensions/sandbox/runner.js (net.Socket.connect, dgram); extmarket.js mountPages (CSP connect-src))</sub>
- **Start programs or commands without your consent** – Server code cannot start programs, workers or foreign code. Packages with their own program are only installed after your explicit consent; you confirm terminal commands yourself. <sub>(enforced in: extsandbox.js (--permission, --disallow-code-generation-from-strings); extpolicy.js DENY_FIRST (terminal, pty, shell, exec); extmarket.js installFromDir PROGRAM_CONSENT; ui/src/extBridge.js TERMINAL)</sub>
- **Change anything without asking you** – Every change through Hostwerk asks you first. Only exception: permissions that explicitly need no confirmation (building the knowledge graph). <sub>(enforced in: extpolicy.js decide() confirm; extmarket.js /call (428 EXT_CONFIRM); extsandbox.js op api)</sub>
- **Act with your login or set cookies** – Pages run in their own empty origin; answers from the server code lose Set-Cookie and never run as a Hostwerk page. <sub>(enforced in: extmarket.js mountPages (CSP sandbox); extsandbox.js proxy (set-cookie entfernt, CSP sandbox))</sub>
- **Replace Hostwerk’s own areas or services** – Own routes only exist under /api/x/&lt;id&gt;/, Hostwerk’s service names are taken. Interface changes only with "override:ui" and your consent. <sub>(enforced in: extsandbox.js proxy (nur /x/&lt;id&gt;), op provide)</sub>
- **Open its own ports** – An extension is only reachable through Hostwerk (/api/x/&lt;id&gt;/), never directly. <sub>(enforced in: extensions/sandbox/runner.js (net.Server.listen, dgram))</sub>

### Sandboxed or part of Hostwerk

| | Sandboxed | Official package with own code |
|---|---|---|
| Who | All extensions from other sources, every page in its frame, own code in developer mode | Packages from the Hostwerk catalog (checksum, signed catalog) with `backend`/`ui` |
| Where the code runs | Page: own empty origin · server code: own process with Node’s permission model | In the Hostwerk process or window |
| Permissions | Technically enforced (block list, permissions, confirmation, blacking out, file/network lock) | Reviewed and signed, but not sandboxed – the limits are a rule, not a lock |

> **To be clear:** official packages with their own code run as part of Hostwerk. For them the limits above are a rule, not a lock. The same applies to your own code if you switch off its sandbox in developer mode.

## 1. Quick start (5 minutes)

**Easiest – the Extension Studio:** *Extensions → For developers → New extension*. A graphical editor guides you
through basics, place in Hostwerk, permissions, content (blocks such as stats, lists, buttons, forms – or your own
code), texts, live preview, check and publishing (GitHub repository with release, submitting to the catalog).

**Option A – in Hostwerk:** *Apps → Extensions → Build own*. Hostwerk creates `<Hostwerk>/extensions/<id>/` with a
working page, texts in German and English and an icon. The page appears in the sidebar immediately; edit the files and
press **Reload** in the page header.

**Option B – on GitHub:** open [hostwerk-ext-template](https://github.com/Passimoritz/hostwerk-ext-template) →
**Use this template**. The repository already contains the check (GitHub Action) and automatic releases.

To try a repository in Hostwerk: *Apps → Extensions → File* (ZIP of the folder) or *From link* (link to a release ZIP).

## 2. The package

```
my-extension/
├─ manifest.json        name, version, permissions, page/tile/settings
├─ icon.svg             square, colourful – shown in the marketplace and the page header
├─ page/
│  ├─ index.html        the page (loads /ext-sdk.js first)
│  └─ app.js            your code (no scripts from the internet – bundle everything)
├─ widget/
│  └─ index.html        optional dashboard tile
└─ locales/
   ├─ de.json           all visible texts in German
   └─ en.json           … and in English
```

At most 10 MB. No programs (`.exe`, `.sh` …) in page-only packages.

## 3. manifest.json

```json
{
  "$schema": "https://raw.githubusercontent.com/Passimoritz/hostwerk-public/main/sdk/manifest.schema.json",
  "id": "player-ticker",
  "name": { "de": "Spieler-Ticker", "en": "Player Ticker" },
  "description": { "de": "Wer ist gerade online?", "en": "Who is online right now?" },
  "version": "1.0.0",
  "author": "Your name",
  "homepage": "https://github.com/you/hostwerk-ext-player-ticker",
  "icon": "icon.svg",
  "hostwerk": ">=3.0.0",
  "sdkVersion": "3.0",
  "permissions": ["read:services", "read:minecraft", "storage"],
  "page":   { "title": { "de": "Spieler-Ticker", "en": "Player Ticker" }, "icon": "users", "file": "page/index.html" },
  "widget": { "title": { "de": "Spieler online", "en": "Players online" }, "file": "widget/index.html", "size": "third" },
  "settings": [
    { "key": "refresh", "type": "number", "label": { "de": "Aktualisieren (Sekunden)", "en": "Refresh (seconds)" }, "default": 10, "min": 3, "max": 120 }
  ]
}
```

| Field | Meaning |
|---|---|
| `id` | a–z, 0–9 and `-`, 2–40 characters. Stays the same forever. |
| `name`, `description`, `title`, `label` | Text or `{ "de": …, "en": … }` – the catalog requires both languages. |
| `version` | `1.2.3`. A higher version shows up as update in Hostwerk. |
| `icon` | Square SVG/PNG in the package – marketplace card and page header. |
| `page.icon` | **Sidebar icon** – a simple line icon like Hostwerk's own areas. One of: `puzzle users monitor gauge activity chart bell book bot box calendar camera clock cloud code coffee cpu database download file flag gamepad gift globe heart home image inbox key dashboard grid leaf line-chart list lock mail map message music network news package pie-chart radio rocket server settings shield cart sparkles star sun swords table tag terminal timer trophy tv wand wifi wrench zap`. |
| `sdkVersion` | The SDK the extension was written for, e.g. `"3.0"` – see [section 19](#19-sdk-30-stability-and-deprecations). |
| `hostwerk` | Minimum version, e.g. `>=3.0.0` – older Hostwerk refuses to install. Or `{ "min": "3.0.0", "max": "3.x" }` with a highest version. |
| `permissions` | What the extension may see and do – see [Permissions](#7-permissions). |
| `network` | Web origins the page may `fetch` (needs the `network` permission), e.g. `["https://api.example.com"]`. |
| `settings` | Form drawn by Hostwerk: `text`, `number` (`min`/`max`), `switch`, `select` (`options`). |

The `$schema` line gives you auto-completion in VS Code.

## 4. The SDK – `Hostwerk.*`

Load it first: `<script src="/ext-sdk.js"></script>`. It also loads the design kit (see 5).

```js
const info = await Hostwerk.ready();           // colours, language, settings, tab, context, action have arrived
const list = await Hostwerk.services();       // [{ id, kind, name, state, port, cpu, memory, startedAt, extra }]
const mc = await Hostwerk.minecraft.servers(); // Minecraft only; extra.players, extra.tps
const stats = await Hostwerk.minecraft.stats(id);

Hostwerk.render('#list', Hostwerk.html`<b>${name}</b>`);   // every ${value} is escaped – safe for player names
Hostwerk.t('summary', { n: 3 });                            // text from locales/<lang>.json, {n} filled in
Hostwerk.fmt.bytes(123456); Hostwerk.fmt.duration(ms); Hostwerk.fmt.time(Date.now());

await Hostwerk.service('web', 'apache').restart();  // asks the user first (needs control:services)
await Hostwerk.minecraft.command(id, 'say Hi');     // asks first (needs command:minecraft)
await Hostwerk.put('/mc/servers/' + id + '/properties', { motd: '§aHi' }); // change a setting (change:minecraft, asks first) – SDK 2.2
await Hostwerk.del('/knowledge/' + id + '/memory/' + entry);               // delete (SDK 2.3)
const dir = await Hostwerk.pickFolder('Choose vault');                     // native folder dialog, path or null (SDK 2.3)
await Hostwerk.terminal('claude', { cwd: dir, title: 'Claude' });           // types into the Hostwerk terminal; the user presses Enter (SDK 2.5, run:terminal)

await Hostwerk.storage.set('pinned', 'srv1');       // kept by Hostwerk (needs storage)
const s = await Hostwerk.settings.get();            // values of manifest.settings
Hostwerk.settings.open();                           // opens the settings dialog

Hostwerk.tab;                         // current tab from page.tabs (SDK 2.2); Hostwerk.setTab('codes') switches it
Hostwerk.context;                     // { kind, id } when shown as a tab on a service page (contributes.tabs)
Hostwerk.on('tab', (id) => …);        // the user picked another tab
Hostwerk.on('action', (a) => …);      // { id, target } – your contributes.action was chosen
Hostwerk.on('service', (s) => …);     // a service changed state
Hostwerk.on('minecraft', (s) => …);   // players joined/left
Hostwerk.on('settings' | 'lang' | 'theme', …);

Hostwerk.toast('Done', { kind: 'success' });
Hostwerk.navigate('/mc/my-server');  // open a Hostwerk area
Hostwerk.openUrl('https://…');       // opens in the browser after asking (also obsidian:// since SDK 2.3)
Hostwerk.copy(text);                 // copies to the clipboard (SDK 2.1)
Hostwerk.get('/system/health');      // raw read access (checked against permissions)
```

`Hostwerk.lang` (`de`/`en`), `Hostwerk.theme` (`dark`/`light`) and `Hostwerk.embed` (`page`/`widget`) tell you where
you are.

## 5. Design kit – Hostwerk's own classes

**Basic requirement:** an extension looks exactly like Hostwerk's built-in areas. That's why `/ext-sdk.css` delivers
Hostwerk's **own** classes, generated from the current app stylesheet. Future design changes reach your extension
automatically. Hostwerk draws the page title, the description and the tabs (`page.tabs`) itself. Your page starts
directly with the content.

| Classes | |
|---|---|
| Layout | `row`, `row-tight`, `stack`, `grid grid-2` / `grid-3` / `grid-4`, `grow`, `right`, `muted`, `small`, `tiny`, `ellipsis`, `mono` |
| Cards | `card`, `card-pad`, `card-head` (with `h3`), `card-body`, `stat` with `k` / `v` / `s` |
| Controls | `btn` (+ `primary`, `ghost`, `danger`, `sm`, `xs`), `input`, `select`, `label`, `seg` (segment buttons), `switch` (`<label class="switch"><input type="checkbox"><span class="track"></span><span class="thumb"></span></label>`) |
| State | `badge` (+ `ok`, `warn`, `err`, `accent`), `callout` (+ `ok`/`warn`/`err`) with `callout-body`, `callout-title`, `progress` |
| Lists | `table`, `list-item`, `setting-row` (with `txt`) |
| Empty / loading | `empty` (+ `h3`, `p`, `empty-action`), `hw-skeleton`, `spinner` |

Colours: `--bg`, `--surface`, `--surface-2`, `--line`, `--line-2`, `--text`, `--text-2`, `--muted`, `--accent`,
`--accent-soft`, `--accent-text`, `--ok`, `--warn`, `--err`, `--mono`. The older `hw-…` classes and `--hw-…`
variables still work, so existing extensions don't break.

**Design scale (Hostwerk 2.11 and newer):** font sizes, radii, spacing and heights only exist as steps – exactly like in
Hostwerk itself. Always pick a step instead of an own number, then your extension keeps fitting after future design changes:

| What | Variables |
|---|---|
| Font | `--fs-2xs` 11 · `--fs-xs` 12 · `--fs-sm` 13 · `--fs-md` 14 · `--fs-lg` 16 · `--fs-xl` 20 · `--fs-2xl` 24 · `--fs-3xl` 28 px |
| Radius | `--r-xs` 4 · `--r-sm` 6 · `--r-md` 8 · `--r-lg` 10 · `--r-xl` 14 · `--r-2xl` 20 · `--r-pill` |
| Spacing | `--sp-1` 4 · `--sp-2` 8 · `--sp-3` 12 · `--sp-4` 16 · `--sp-5` 20 · `--sp-6` 24 · `--sp-8` 32 px |
| Height of buttons/fields | `--control-h` 34 · `--control-h-sm` 28 · `--control-h-xs` 24 px |
| Readable status colours for text | `--ok-text`, `--warn-text`, `--err-text` (the base colours `--ok` etc. are for areas and dots) |
| Main button, fields | `--accent-btn`, `--input-bg` |

All of them also exist with the `--hw-` prefix (e.g. `--hw-fs-sm`). The most important action of a page is a `btn primary`;
only Hostwerk's own "+ New" button carries the gradient.

**Accent colour (Hostwerk 2.12 and newer):** the user picks ONE accent colour (Settings → General) – or a profile
brings its own. Hostwerk derives a complete, readable palette from it, separately for light and dark (OKLCH, contrast
checked with the WCAG formula), and sends it to your extension live, also while the user is still choosing:

| Variable | Use | Guarantee |
|---|---|---|
| `--accent` | the chosen colour itself: borders, switches, selection dots | exactly what the user picked |
| `--accent-btn` | background of `btn primary` | white text on it ≥ 4.5:1 |
| `--accent-text` | links, icons and text in accent colour | ≥ 4.5:1 on every surface, also on `--accent-soft` |
| `--accent-soft` | subtle background (selected row, chip) | transparent tint |
| `--accent-contrast` | text placed directly on `--accent` | white or near-black, ≥ 4.5:1 |
| `--accent-ring` | focus outline | ≥ 3:1 on every surface |
| `--accent-2` | harmonious second colour (charts, prompts) | ≥ 3:1 on every surface |
| `--grad` | gradient for highlights | follows the accent |

**Never hard-code your brand colour for UI chrome** (buttons, links, focus, selection, tabs) – use `--accent*`. Then
your extension follows the user's colour and stays readable in both themes, even for yellow, cyan or grey. Your brand
colour belongs in your logo or icon only.

Rules the check enforces (warnings – errors in the catalog): no fixed colours, no own fonts (`var(--mono)` is fine),
nothing laid over Hostwerk (`position: fixed`, huge `z-index`). A deliberate exception per file, with a reason:
`/* hostwerk-allow: colors, fonts – preview like in the game */`.

### Design: what a Hostwerk page looks like

Extensions follow the same rule book as Hostwerk itself:
**[“So sieht eine Hostwerk-Seite aus”](ui-guidelines.md)** (German). In short:

- **Core building blocks instead of home-made ones**: cards `card`/`card-head`/`card-body`, key figures `card stat`
  (`v text` for text values, `of` for “/ total”), state `<StatusPill>`/`badge ok|warn|err`, empty `<Empty>`/`<TileEmpty>`,
  loading `<Loading>`/`hw-skeleton`, confirming `confirmDialog` – never `window.confirm`, no own spinners.
- **Page head** (native pages only – framed pages get it from Hostwerk): icon + title, **one** sentence as `<p>`,
  actions on the right; longer explanations as ⓘ.
- **Buttons**: one `primary` action per area, rightmost; “Cancel” to the left of it. A button that first opens a dialog
  ends with “ …”. No exclamation marks, no “successfully” in messages (`toast.success('Saved')`).
- **Words** in `locales/de.json`: Sicherung (not Backup), Dienst (not Service), Passwort (not Kennwort), Ordner (not
  Verzeichnis), Anmeldung (not Login), neu starten (not neustarten), “Lädt …” for progress, “…” instead of “...”.

The checker reports deviations as hints with the code `ui-…` (no points deducted), e.g.
`· [ui-text-empty] empty card as a grey sentence – use <TileEmpty …>`.

**Space – pages without scrolling (Hostwerk 3.1 and newer):** a page fits on one screen at 1366×768; long lists scroll in
their own area. Native extensions use the components from `@hostwerk/ui`, pages in the frame the same classes from

## 8. Settings, storage, events

- **Settings**: describe them in `manifest.settings`; Hostwerk draws the form (so it always fits the design) and sends
  changes live (`Hostwerk.on('settings')`).
- **Storage**: `Hostwerk.storage.get/set/remove/all` – JSON values, 256 KB per extension, removed with the extension.
  Browser storage (`localStorage`, cookies) does not work in the sandbox.
- **Events** instead of polling: `service` (state changes), `minecraft` (players). Poll slowly (≥ 10 s) for the rest.
  Server modules (`backend`) listen on Hostwerk's event bus: `host.core('events').bus.on('broadcast', fn)` – e.g.
  `{ type: 'mc-player-join', id, server, player }` and `{ type: 'mc-player-leave', id, server, player, ms }` (`ms` = length of the session).

## 9. Dashboard tiles

`widget.file` is a small page without its own padding/background – Hostwerk draws the card. The height follows the
content automatically. Sizes: `third`, `half`, `full`. Installed tiles appear on the overview; users show, hide and arrange them with *Customize*.

## 11. Publish: repository, release, submit

1. Put the extension in its **own GitHub repository** (template: *Use this template*).
2. Raise `version` in `manifest.json`, add a line to `CHANGELOG.md`, push a tag `v1.2.3`.
   The Action checks the package and creates a release with `<id>-<version>.zip` and a `.sha256` file.
3. In Hostwerk: *Submit* on the installed extension – or open
   [Submit an extension](https://github.com/Passimoritz/hostwerk-public/issues/new?template=extension.yml) and paste
   the release link.
4. The action checks again (`--strict`), keeps a copy with checksum in `packages/` and adds it to
   `catalog/community.json`. Pages and tiles are added at once; services wait for a person (label *approved*).
5. Updates: submit again with a higher version (same id – an id belongs to whoever submitted it first).

Test without submitting: *Actions → Add extension → Run workflow* with a package link (dry run).

## 13. Security model

- The page runs in a **sandboxed iframe with its own opaque origin** – no access to Hostwerk's login, cookies or API.
- Content-Security-Policy: scripts only from the package, network only to the origins in `network`, no frames,
  no forms posting elsewhere.
- Every request goes through the bridge and is checked against the permissions on the **server**; changes need the
  user's confirmation every time.
- Catalog packages are pinned by **SHA-256** – Hostwerk installs exactly the checked file.
- Own server code (`backend`) from outside the Hostwerk catalogue runs in a **separate, sandboxed process**; certain areas (settings, passwords, keys, other extensions …) are never available, and secrets in answers are blacked out. Details: [Extensions explained](../docs/extensions.md).

## 15. SDK 2.7: look, dependencies and native extensions

**Look on the extension page.** Hostwerk shows every extension with its icon, a banner and its category.

| Field | Meaning |
|---|---|
| `category` | One of `games`, `network`, `security`, `monitoring`, `developer`, `ai`, `communication`, `other` – the chips on the extension page. |
| `color` | Accent colour `#rrggbb` for card and banner. |
| `banner` | Wide picture (SVG/PNG, about 1280×400) for the detail view and featured cards. |
| `screenshots` | Up to 6 pictures (`docs/screenshot.png` …) for the detail view. |

Animated icons and banners are welcome – but every animation has to stop under `@media (prefers-reduced-motion: reduce)`
(the check fails otherwise).

**Dependencies.** `"requires": { "game-servers": ">=1.0.0" }` – Hostwerk installs what is missing first (from the
catalogue), refuses circles and does not remove an extension others still need (unless the user forces it).
Ranges: `*`, `1.2.3`, `>=1.2.0`, `^1.2.0`, `~1.2.0`.

**Native extensions** run as part of Hostwerk – this is how features that used to be built in (password manager, game
servers, mail server, router …) became extensions. They need the permission `native` and bring:

- `backend`: `server/index.js` with `activate(host)` – own API routes (`host.router`, same sign-in as Hostwerk;
  `host.publicRouter` without), `host.provide(name, service)` for Hostwerk and other extensions, hooks
  `host.on('autostart' | 'shutdown' | 'upgrade')`, Hostwerk's building blocks `host.core(name)`, `host.service(name)`,
  `host.lib(name)`, texts `host.t(text, vars)`, `host.error(status, text)`, `host.broadcast(msg)`.
- `ui`: `ui/index.js`, built with `node sdk/build-native.js .` from `ui/src/index.jsx` (React, `@hostwerk/api`,
  `@hostwerk/ui`, `@hostwerk/kit`, `@hostwerk/i18n` …). Export `{ pages: { main }, slots: { … } }` – slots place
  tabs and buttons inside Hostwerk (`project.tabs`, `live.tabs`, `mc.connect`, `files.preview`, `mail.tabs`,
  `titlebar`, `machines.board`, `tasks.tabs`, `dashboard.actions` – a button next to “Customise” on the overview, `sidebar.footer` – next to the version at the bottom of the sidebar, `live.remote.actions` – buttons at remote access, SDK 3.4). Since SDK 3.4 also `screens` – a whole screen of its own (section 26).
- Texts in the code are English; `locales/de.json` maps the English text to German (`$patterns` for texts with parts).
- Data stays where Hostwerk always kept it – removing the extension deletes nothing.

**Security updates for your own programs** (Hostwerk 2.11+, used since 2.13 by the mail server and game servers). If a
native extension brings a program with contact to the internet, it registers it with Hostwerk's security updates – then
patches arrive by themselves like for PHP and the databases, with a trial run and fallback (`keeper.attempt`), and show up
under *Settings → Updates* with their own switch:

```js
// server/index.js
exports.activate = (host) => {
  const pu = host.ctx.patchUpdates;               // missing before Hostwerk 2.11 – so check
  if (pu && typeof pu.register === 'function') {
    const off = pu.register('my-service', {      // id: a–z, 0–9, - (2–40 characters)
      labels: { de: 'Mein Dienst', en: 'My service' },
      items: () => [{ key: 'my-service', label: 'My service', version: '1.4.2' }],            // what is installed
      updates: async () => [{ key: 'my-service', label: 'My service', current: '1.4.2', latest: '1.4.3', target: rel }],
      plan: (u) => ({
        install: async () => { /* put the new version NEXT TO the old one */ },
        probe: async () => { /* check, throw on failure – e.g. trial run, restart running services */ },
        activate: async () => { /* only now remove the old version */ },
        discard: async () => { /* remove the new version, start services on the old one again */ },
      }),
    });
    host.on('shutdown', () => off());             // unregister on removal/update
  }
};
```

Hostwerk checks every 6 hours, installs only what the person did not exclude, remembers failed versions (self-maintenance
`patch-<key>`) and skips them until a newer one appears. Only offer patch versions of the same series – larger jumps are
the person's decision.

**Reading web server logs** (Hostwerk 2.12 and newer). `host.ctx.web.logFiles(inst)` names a web server's logs without
creating anything: `{ access, error, php, rotated: { access: [...], error: [...], php: [...] } }` – `rotated` are the
packed versions (`.log.gz`, newest first). The access log uses the **vcombined** format (Apache `%v:%p` first, nginx
`$server_name:$server_port`) with the duration at the end (Apache µs, nginx seconds); Caddy writes JSON with
`request.host`. That allows statistics per domain:

```js
const web = host.ctx.web;
for (const inst of web.list()) {
  const f = typeof web.logFiles === 'function' ? web.logFiles(inst) : null; // missing before 2.12
  if (f) count(f.access, f.rotated.access);
}
```

Since SDK 2.8, server code from outside the official catalogue runs **sandboxed** (see section 16); only official
packages (pinned by SHA-256) run as part of Hostwerk and may bring their own interface module.

**Own server code from any source.** A `backend` no longer needs the Hostwerk catalogue: everything else runs in a

programs, no local network, no access to Hostwerk's settings or keys. Routes live under `/api/x/<id>/…`
(public: `/api/x/<id>/pub/…`); the page reaches them with `Hostwerk.backend(method, path, body)`. `host.api()`
asks Hostwerk with the extension's permissions; answers arrive with secrets blacked out. Own interface modules (`ui`)
stay reserved for official packages – others show their page in the frame.

### Keyboard shortcuts

Extensions can bring their own shortcuts. People see them in the shortcut overview (F1) and can change, switch off or
reset them under **Settings → General → Shortcuts**, together with Hostwerk's own.

```json
"contributes": {
  "shortcuts": [
    { "id": "open-logs", "title": { "en": "Open logs", "de": "Protokolle öffnen" }, "keys": "ctrl+alt+l", "action": "logs" }
  ]
}
```

| Field | Meaning |
|---|---|
| `id` | a–z, 0–9, `-`. Hostwerk registers it as `ext:<extension id>:<id>` – that is also the key in the user's settings. |
| `title` | Text in the overview and the settings (`{ "en", "de" }` or one string). |
| `keys` | One combination: modifiers `ctrl`, `alt`, `shift`, `meta` + one key (`a`–`z`, `0`–`9`, `f1`–`f24`, `enter`, `arrowup`, `,` …), e.g. `ctrl+alt+p`. Ctrl and ⌘ count as the same. Needs `ctrl` or `alt` – only F keys may stand alone. |
| `action` | What it does: the id of a page tab (opens it), of `contributes.actions` (runs it like from the search) or of `contributes.new`. Without `action` the shortcut opens the extension page. |

Rules: up to 20 shortcuts. Copy, paste, cut, select all, undo/redo, Alt+F4, Ctrl+W/Q/Tab and the like are reserved – the
check fails. An extension **never takes a shortcut away from Hostwerk**: if `keys` is one of Hostwerk's own (Ctrl+K,
Ctrl+N, Ctrl+1…9, F1 …), the check warns and the shortcut stays off until the user assigns it (settings show the
conflict with a “Use anyway” button). Two extensions with the same keys: the first one installed wins, the other is
shown as a conflict.

Native extensions (official packages with an interface module) can export shortcuts with code instead:
`export default { pages, slots, shortcuts: [{ id: 'quick-open', title: 'Open quickly', keys: 'ctrl+alt+o', run: () => … }] }`
– the title is English, German comes from `locales/de.json`.

### Language packs

Hostwerk itself maintains German and English. More languages come from extensions: list them in `manifest.json` → `"languages": [{ "id": "fr", "name": "Français", "file": "lang/fr.json" }]`. The file has the same shape as Hostwerk's `ui/src/i18n/en.json` – `{ "texts": { "<German text>": "<translation>" }, "patterns": [["text with {}", "translation with {}"]] }`. Users pick the language under Settings → General; whatever is missing appears in English. The checker validates the file and the placeholders.

| `hostwerk-ext-template-override` | Replaces the overview greeting, adds a tip to the empty web server list |
| `hostwerk-ext-template-extend` | A tab, a header action and settings on another extension – with its author's consent |
| `hostwerk-ext-template-service-tab` | Tabs on service pages, right-click and quick search entries, a shortcut |
| `hostwerk-ext-template-backend` | Own server code, sandboxed in its own process, with a tested logic module |

### Themes (`contributes.themes`)

A theme is **not CSS**. It sets values for a fixed list of design variables; Hostwerk builds the stylesheet itself, so
nothing can be injected and nothing loads from the internet.

```json
"contributes": {
  "themes": [{
    "id": "northern-light",
    "title": { "de": "Nordlicht", "en": "Northern light" },
    "tokens": {
      "dark":  { "--bg": "#0b1416", "--surface": "#132126", "--text": "#e6f1f2", "--muted": "#91aab0" },
      "light": { "--bg": "#f2f7f7", "--surface": "#ffffff", "--text": "#102226", "--muted": "#4f656b" }
    },
    "accent": "#0d9488", "accents": ["#0d9488", "#3b82f6"],
    "radius": 1.3, "density": "normal",
    "fonts": [{ "family": "Inter", "file": "fonts/inter.woff2", "weight": "100 900" }], "font": "Inter"
  }]
}
```

| Field | Rule |
|---|---|
| `tokens.dark` / `tokens.light` | Only `--bg`, `--bg-2`, `--surface`, `--surface-2`, `--surface-3`, `--line`, `--line-2`, `--text`, `--text-2`, `--muted`, `--ok`, `--ok-text`, `--warn`, `--warn-text`, `--err`, `--err-text`, `--info`, `--console-bg`, `--input-bg` (as `#rrggbb`), `--ok-soft` … `--info-soft` (also `rgba()`), `--shadow`, `--shadow-lg`. Missing ones keep Hostwerk's values. |
| `accent`, `accents` | Suggested accent (used while the user has none of their own) and up to 8 more suggestions. Hostwerk derives `--accent-text`, `--accent-btn`, `--accent-ring` … for **the theme's surfaces**, so they stay readable. |
| `radius` | 0 (square) … 1 (Hostwerk) … 2 (very round) – scales `--r-*`. |
| `density` | `compact`, `normal`, `comfortable` – scales `--sp-*` and control heights. |
| `fonts`, `font` | Font files in the package (`.woff2` preferred, max. 1.5 MB together). |

**Contrast check (WCAG 2.2 AA)** – in `check.js` *and* again right before Hostwerk applies a theme: every pair the theme
touches is calculated – `--text`, `--text-2`, `--muted`, `--ok-text`, `--warn-text`, `--err-text` ≥ 4.5:1 on all five
surfaces (and `--text` on `--input-bg`), `--ok`, `--warn`, `--err`, `--info` ≥ 3:1, the accent ≥ 3:1. Dark stays dark,
light stays light. A failing theme is listed (with the reason) but never applied.

People pick it under *Settings → General → Appearance → Theme*. Switching is instant (one style element, no re-render,
remembered for the next start), the accent picker shows the theme's suggestions, and removing the extension brings back
Hostwerk's own look.

### Overrides of Hostwerk's own interface (`contributes.overrides`)

Overrides replace or extend **named places** (slots) of Hostwerk's interface. A slot is a whole region – never a button
in every card – so an override runs once per page.

| Slot | Where | Modes |
|---|---|---|
| `dashboard.hero` | Greeting at the top of the overview | `replace`, `before`, `after` |
| `web.empty` | Empty web server list | `replace`, `after` |
| `dbs.empty` | Empty database server list | `replace`, `after` |
| `minecraft.empty` | Empty Minecraft server list | `replace`, `after` |

```json
"permissions": ["override:ui"],
"contributes": {
  "overrides": [
    { "id": "hero", "slot": "dashboard.hero", "mode": "replace", "title": { "de": "…", "en": "…" },
      "file": "overrides/hero.html", "preview": "docs/hero-preview.svg", "height": 160 }
  ]
}
```

The page runs sandboxed like every extension page (`Hostwerk.context = { kind: "override", slot, id }`, `Hostwerk.embed`
is `override`, transparent background, the frame grows up to `height`, max. 480 px). Official packages with an interface
module may export a component instead: `export default { overrides: { hero: ({ slot, props, Original }) => … } }`.

**Safety net**

- Permission **`override:ui`** (high risk) – listed before installing; without it Hostwerk delivers no override.
- **Consent with preview:** outside official packages nothing is active until the user agrees in the extension's detail
  view (*Look and allow …*). The dialog lists every place, how it changes it and the `preview` picture. *Look first*
  switches it on for this session only, with *Allow* / *Discard* right above the override. Consent is bound to the
  places: a new place or mode in an update asks again.
- **One click off:** every override carries “Changed by …” with *Switch override off*; the detail view can switch it back on.
- **Fallback to the original:** a crashing component or a page that does not report within 4 seconds is replaced by
  Hostwerk's original, with a note. Of several `replace` overrides only the first (official first, then `order`) is used.

**Special review (catalog).** `check.js` returns `review: ["override:ui"]` and runs extra checks on every override page
(errors): **performance** – page plus own scripts/styles ≤ 100 KB, no `setInterval` faster than one second;
**accessibility** – `<html lang>`, a name for every button, `alt` for every image, no `tabindex` above 0, no removed focus
outline; **translations** – every `data-i18n` key and `Hostwerk.t('key')` in both `locales`; **network** – no `fetch`,
`XMLHttpRequest`, `WebSocket`, `EventSource` or `sendBeacon` without the `network` permission. After that a person checks:

1. Does it serve the user (requirement clear, no advertising, no dark patterns, no hidden data collection)?
2. Does the original stay reachable (nothing important hidden, *Switch override off* not covered)?
3. Same look as Hostwerk: design kit classes, `var(--…)` colours, light and dark, phone width?
4. Keyboard and screen reader: order, focus visible, names, `prefers-reduced-motion`?
5. German and English complete and natural?
6. Only the permissions it needs; does the `preview` picture match what it does?
7. Does it still work when the slot is empty, the user is offline or the language changes?

### Extending other extensions (`contributes.extends`)

An extension may add to **another extension** – but only as far as that extension's author allows.

| Point | The add-on (`contributes.extends[]`) | The author of the target (`allowExtensions`) |
|---|---|---|
| `tabs` | `"tabs": [{ "id", "title", "file", "icon" }]` – tabs on its page | `"tabs"` |
| `actions` | `"actions": [{ "id", "title", "icon" }]` – buttons in its header that open the add-on's page | `"actions"` |
| `settings` | `"settings": true` – the add-on's settings inside its settings dialog | `"settings"` |
| `locales` | `"locales": { "de": "…json", "en": "…json" }` – rewords **existing** texts | `"locales"` (only by id) |
| `page` | `"page": { "file": "…html" }` – replaces its page (with *Show original*) | `"page"` (only by id) |

```json
// add-on
"permissions": ["extend:extensions"],
"contributes": { "extends": [{ "id": "my-extension", "version": ">=1.0.0", "tabs": [ … ], "actions": [ … ], "settings": true }] }
// target – written by ITS author
"allowExtensions": { "my-addon": ["tabs", "actions", "settings"], "*": ["tabs"] }
```

- **The original author has the rights.** Without an entry nothing appears; `"*"` can never grant `page` or `locales`.
  Removing an entry in a new version takes the permission back – the addition disappears by itself.
- **No permission escalation:** tabs, pages and actions of the add-on run with the **add-on's** permissions, not the target's.
- **Precedence:** own tabs and actions first, then those of add-ons (install order). If two add-ons may replace the page,
  the one the author names first in `allowExtensions` wins; the other is shown as a conflict. Text overlays only change
  keys the target already has. `version` keeps an addition off for versions the add-on was not made for.
- **Transparency:** the add-on's detail view shows “Extends *X* – with consent from *author*” (or “Waiting for permission
  from …”), the target's shows “Extended by …”; users can switch additions off.
- Native targets (official packages with an interface module) get `page`, `settings`, `locales` and since SDK 2.10 `tabs` (as a bar above
  their page); actions need a page frame.

## 19. SDK 3.0: stability and deprecations

From Hostwerk 3.0 on, the core only gets fixes, security, accessibility and translations – new things come as
extensions. That only works if extensions keep running. So SDK 3.0 makes a promise:

- **Semantic versioning.** Everything SDK 3.0 documents (`window.Hostwerk`, manifest fields, permissions, `contributes`)
  works with **every Hostwerk 3.x**. Minor versions only add, patch versions only fix.
- **Nothing disappears within 3.x.** Something is removed only with a new major version (SDK 4.0) – and only after it was
  deprecated for **at least two minor versions and 12 months**. The check warns about everything deprecated, with the date
  and the replacement:
  `Old permissions "read"/"write" – … Deprecated since SDK 3.0.0 (2026-10-21); removed no earlier than SDK 4.0.0 and not before 2027-10-21.`
- **Experimental APIs are not part of the promise.** They can change in any version, you have to opt in, and they are
  not allowed in the catalog (like the “Proposed API” in VS Code):

  ```json
  "experimental": ["name-of-the-api"]
  ```

  At the moment there are no experimental APIs – the list is in `EXPERIMENTAL` in `check.js`.

### `sdkVersion` and `hostwerk.max`

```json
"sdkVersion": "3.0",
"hostwerk": { "min": "3.0.0", "max": "3.x" }
```

| Field | Meaning |
|---|---|
| `sdkVersion` | The SDK you wrote and tested the extension for (`major.minor`). Hostwerk with SDK 3.4 runs everything written for 3.0–3.4; an extension written for a newer SDK says “please update Hostwerk”. Written for 2.x: still runs (3.0 keeps everything from 2.x), the check gives a hint. |
| `hostwerk` | As before `">=3.0.0"` (minimum only) – or `{ "min": "3.0.0", "max": "3.x" }`. `max` is inclusive: `"3.x"` (every 3.x), `"3.4.x"` or an exact version. Use it only when you know a later version breaks your extension. |

New extensions from the studio, the AI draft and the templates get `sdkVersion` automatically. Without `sdkVersion` the
check only shows a hint – no points are deducted.

## 20. SDK 3.1: shared site check and notes in the knowledge graph

Hostwerk 3.0 and newer. Minor version – only additions, everything from 3.0 keeps working.

**Site check as a service** (*native*): `host.service('sitecheck')` is Hostwerk's own site check – the same one as
*Projects → Site check*. Two functions:

```js
const sc = host.service('sitecheck');                 // throws on Hostwerk before 3.0 – check, keep an own fallback
const r = await sc.checkDir('/path/to/dist', { base: '/my-repo/', max: 60 });   // built folder, nothing uploaded
const s = await sc.crawl('http://localhost:8080/', { max: 60 });                // running site
// → { pages: [{ url, status, ms, title, issues: [{ level: 'err'|'warn'|'info', text }] }], broken: [{ url, kind, status, foundOn }], summary }
```

`checkDir` serves the folder for a moment on `127.0.0.1` under `base` (GitHub project pages live under `/<repo>/`), so
links starting with `/` that point past `base` show up as broken – exactly as they would after publishing. Texts are German
like Hostwerk's own check. *Publish static sites* uses it before every upload.

**Notes as nodes in the knowledge graph** (permission `change:knowledge`, no prompt; native: `ctx.knowledge.setNotes(id, notes)`):

```js
await Hostwerk.put('/knowledge/notes', { notes: [
  { id: 'web:apache', title: 'Web server “Apache”', text: '- [ ] renew certificate\nUses `UserController`', service: { kind: 'web', id: 'apache' } },
] });
```

The call replaces all notes of the extension (`[]` removes them). Hostwerk sets the sender itself – an extension can only
change its own notes. Every note becomes a document node (heading, `#tags`, `[[links]]`, named classes as edges) in the
source “Notes from Hostwerk” and in every project the service belongs to (web server or app of the project) or that the note
names in `projects: [projectId]`. `GET /knowledge/notes` (permission `read:knowledge`) lists what is in the graph.
*Service notes* uses it.

**Moving data of extensions between machines** (*native*): `host.transfer.register({ label, export({ dir, job }), import({ dir, job, test }) })`
– `export` puts files into `dir`, `import` reads them on the target machine (the same extension has to run there). The
data shows up as its own line in *Move* (also when moving several things at once). Gone when the extension is removed.

```js
host.transfer.register({ label: { de: 'Postfächer', en: 'Mailboxes' },
  export: async ({ dir, job }) => { job.progress(30, 'Packing mailboxes …'); /* copy files into dir */ },
  import: async ({ dir, job, test }) => { /* take the files from dir */ return { boxes: 3 }; } });
```

**Hostwerk's address for pages in a frame:** `Hostwerk.info().app.origin` (e.g. `http://192.168.1.5:7800`) and
`Hostwerk.info().app.publicView` – the full address of the own public view `/v/<id>/` (or `null`), e.g. to show it for OBS.

**Move a port to a wanted one:** `POST /system/ports/fix` (permission `change:ports`) takes `to` besides `{ kind, id, field }`

## 21. SDK 3.2: sections instead of tabs, file browser and pages in a web server

Hostwerk 3.0 and newer (the new places exist from the Hostwerk version with SDK 3.2). Minor version – only additions.
Not everything needs its own tab: what belongs to a detail view now appears **right there** as a section.

**Sections** (`contributes.sections`, sandboxed – or native through the module field `sections`):

```json
"contributes": {
  "sections": [{ "id": "preview", "title": { "de": "MOTD", "en": "MOTD" }, "icon": "sparkles", "on": "mc.overview", "file": "page/section.html", "height": 360 }],
  "tabs": [{ "id": "motd", "title": "MOTD", "on": "minecraft", "file": "page/tab.html", "fallback": true }]
}
```

| `on` | Where | `Hostwerk.context` |
|---|---|---|
| `mc.overview` | Minecraft server → Overview (below “How players see your server”) | `{ kind: 'minecraft', id, place, section }` |
| `mc.players` | Minecraft server → Players → Manage | `{ kind: 'minecraft', id, place, section }` |
| `files.folder` | Files → right side while no file is open (about the open folder) | `{ kind: 'folder', root, path, place, section }` |
| `web.site` | Web server → Overview | `{ kind: 'web', id, place, section }` |

- Hostwerk draws the card (title, puzzle mark with info, collapse – remembered by the browser). The page runs sandboxed in
  a frame (`Hostwerk.embed === 'section'`) and grows with its content up to `height` (at most 900 px).
- At most two sections per extension and place. If the page does not answer within 6 seconds or a native section crashes,
  a note with “Try again” appears there – the detail view keeps working.
- **Fallback for older Hostwerk versions:** a tab with `"fallback": true` only shows on versions without sections, so the
  extension needs no higher minimum version.
- From a section to the own page with an action: `Hostwerk.navigate('/ext/<id>?action=edit&target=<id>')` (since 3.2 with a simple query).
- **Whole page inside a main area:** a tab with `"page": true` (only `on: "area:…"`, `file` = `page.file`) shows the
  complete extension page as a tab of that area – e.g. `"on": "area:ai"` → AI assistant → your tab. The area header and tab
  bar stay, `page.tabs` become a list on the left (like the settings), the address is `#/ki/<tab id>/<sub tab>` (areas
  whose address holds a service id use `x-<extension>-<tab>`). `#/ext/<id>`, the search and `Hostwerk.navigate('/ext/<id>/<tab>')`
  lead there, so combine it with `"nav": false` in `page`. Older Hostwerk versions show `file` as a plain tab.
- Native: `export default { sections: { 'mc.overview': [{ id, title, icon, order, when(ctx), Component }] } }` –
  `Component` gets `ctx` plus `server` (Minecraft) or `web` (web server) as props; `when(ctx) === false` hides it.

**File browser** (native through `slots`, sandboxed through `contributes.actions`):

```js
slots: {
  'files.actions': [{ id: 'view-3d', title: 'View in 3D', icon: Box, when: (e) => !e.dir && /\.schem$/i.test(e.name), run: (e) => e.open() }],
  'files.marks': [{ id: 'shared', icon: Share2, marks: async ({ root, path }) => ({ 'worlds': { title: 'Shared with Anna' } }) }],
}
```

- `files.actions`: entries in the right-click menu (entry, and empty space = open folder). `e = { root, path, dir, name, open() }`
  – `open()` shows the file in Hostwerk's preview.
- `files.marks`: small mark after the name (with tooltip) – reload with `window.dispatchEvent(new Event('hw:files-marks'))`.
- Sandboxed: `contributes.actions` with `"on": ["folder"]` or `["file"]` – opens the own page with
  `?action=<id>&kind=folder&target=<root>:<path>` (like the right-click actions of services).
- Previews for file types as before through `files.preview` (`{ id, title, match: /…/, Component({ root, path }) }`).

**Provide pages in a web server** (*native*, `host.sites`): an extension offers a page, Hostwerk writes it into a subfolder
of a web server (docRoot or vHost) and renews it at the chosen interval – without Hostwerk sign-in and without an open
Hostwerk port. *Web server → Overview → Pages from extensions* shows what lives where.

```js
if (host.sites) host.sites.register({ id: 'board', title: { de: 'Bestenliste', en: 'Leaderboard' }, defaults: { limit: 10 },
  render: async (options, { lang }) => ({ 'index.html': page(options, lang), 'data.json': JSON.stringify(await data(options)) }) });
host.sites.targets();                 // [{ id, web, vhost, label, base }] – web folders to choose from
host.sites.list();                    // own pages: [{ id, kind, web, vhost, sub, options, interval, on, url, writtenAt, error }]
await host.sites.save({ kind: 'board', web: 'apache', vhost: null, sub: 'leaderboard', options, interval: 60, title }); // new/change (with id)
host.sites.remove(id); await host.sites.publish(id);
```

- The target is always a web folder of a Hostwerk web server plus **one** simple subfolder (`[a-z0-9_-]`). A folder with
  other files is not taken over; Hostwerk leaves `.hostwerk-site.json` as a marker and only deletes its own files when
  removing. At most 12 files (`.html .json .css .js .svg .txt`), 2 MB together, interval 30 s – 24 h.
- `render()` must return `index.html` and gets the settings (defaults + saved). **Only public data** – the page is readable
  by anyone who reaches the web server.
- Hostwerk opens the own page with an action through `?action=site&target=<page id>` (button “Settings” in the list).
- While the extension is not running, the page keeps its last state (note in the list). Without `host.sites` (older
  Hostwerk, running sandboxed) simply skip it.

```js
exports.activate = (host) => {

    versions: async () => ({ latest: 'latest', versions: [{ id: 'latest', stable: true }] }),
    latestBuild: async () => '2104',
    download: async (version, dest, job) => ({ build: '2104' }), // put the file at dest, check its checksum
    java: () => 21,
    launchArgs: (s, jar) => ['-jar', jar],                       // instead of "-jar server.jar nogui"
    beforeStart: (s, dir) => { /* e.g. write the port into its own config */ },
    readyRe: /Listening on \//,                                  // instead of "Done (…s)!"
  }, host.id);
  host.on('shutdown', off);
};
```

Built-in types (paper, velocity …) cannot be replaced. Without the extension a created server stays in the list and keeps
starting with `-jar server.jar nogui`.

**Bedrock and capabilities** (3.x, feature detection): the core knows the type `bedrock` (Bedrock Dedicated Server, no
Java, UDP). Instead of comparing type names ask `ctx.minecraft.caps(server)` → `{ edition: 'java'|'bedrock', java,
protocol: 'TCP'|'UDP', addons: 'plugins'|'mods'|null, worlds, datapacks, lists: 'java'|'bedrock'|null, … }` or
`ctx.minecraft.isBedrock(server)`. Bedrock servers have `port` and `portv6` (both UDP), no plugins and no whitelist/ops
(instead `minecraft.bedrock.lists(id)` with allow list, permissions and known players with their XUID). Create it like
any type: `minecraft.create({ type: 'bedrock', name, eula: true })`.

**Forced hosts for Velocity**: `ctx.minecraft.network.apply(proxyId, { members: [{ id, key }], forcedHosts: { "survival.example.org": ["survival"] } })`
writes the addresses into `[forced-hosts]` of velocity.toml (valid domain, target must be in the network – otherwise an error
before anything changes). Without `forcedHosts` the section stays empty as before. BungeeCord proxies are set up by the extension.

**Security**: servers behind a proxy (`network.proxy` set) listen on 127.0.0.1 only and do not check accounts –
`security.publicPorts()` no longer lists them; firewall and router automation never open them.

**Move**: whoever uses Geyser, a proxy or a network gets "Minecraft server network" (formerly "Bedrock bridge") with the
update – it reads the same data (`settings.minecraft.servers[].geyser`) and keeps ports and Floodgate keys.
## 23. SDK 3.2: loading like a built-in page

Hostwerk 3.0 and newer (with the 3.2 SDK). Minor version – only additions, every page keeps working without changes.

**Hostwerk shows the loading animation.** While a page, tab or tile in a frame loads, Hostwerk draws the same skeleton as
for its own pages over the frame and shows the frame once the page reports *loaded*. The SDK does that by itself – after
the first `Hostwerk.render(…)` (after `Hostwerk.ready()`), or once the page shows content and is quiet for a moment
(at the latest 8 s after `ready`). If a page does not answer at all, Hostwerk shows “The extension is not responding” with
**Try again** instead of an empty area. Older pages without the signal are shown after at most 10 s.

Pages that need their data before anything makes sense keep the animation and report themselves:

```html
<meta name="hostwerk-loading" content="manual">   <!-- or: Hostwerk.holdLoaded() right at the start of the script -->
```

```js
await Hostwerk.ready();
render(await Hostwerk.get('/system/ports'));
Hostwerk.loaded();                                  // now Hostwerk shows the page
```

**Same states inside the page** – for parts that load later, in the design kit:

```js
Hostwerk.ui.loading('#list', { rows: 4 });          // placeholder rows, aria-busy + announcement for screen readers
Hostwerk.ui.error('#list', err, reload);            // message (role=alert) with “Try again”, calls reload()
await Hostwerk.ui.load('#list', async () => {       // both in one: loading → your code renders → or error with retry
  Hostwerk.render('#list', Hostwerk.html`…${await Hostwerk.get('/apps')}…`);
});
Hostwerk.html`<div>${Hostwerk.ui.skeleton(3)}</div>`; // just the placeholder rows
```

Texts come in German and English; your own via the keys `hw.loading`, `hw.loadError`, `hw.retry` in `locales/*.json`.
`Hostwerk.ui.loading` does not count as *loaded*; `error` and every other `render` do.

**More robust connection:** the SDK repeats its hello until Hostwerk answers and keeps calls made before that (e.g.
`Hostwerk.get` right at the start) until then – nothing is lost any more when the frame is faster than Hostwerk. Every
message carries the id of the document, so answers of a frame that was reloaded in between are no longer mixed up.

## 24. SDK 3.2: without an own sidebar entry

Hostwerk 3.0 and newer (with the 3.2 SDK). Only additions – older Hostwerk versions ignore the new values and keep showing the entry.

The sidebar holds Hostwerk's areas. An extension that belongs to one of them appears **there** – as a tab, a section or a
tile – instead of adding one more sidebar entry:

```json
"page": { "title": { "de": "Router", "en": "Router" }, "icon": "router", "nav": false }
```

- `"nav": false` = no own sidebar entry. The page stays reachable from *Extensions → Open*, the puzzle mark, the command
  palette, *Settings → Extensions* and `Hostwerk.navigate('/ext/<id>')`. People can still pin it under
  *Settings → General → Sidebar* (switch on). The checker warns if the extension then has no other place
  (`contributes.tabs`/`sections`/`actions`, a native `ui` with slots, a dashboard tile).
- Where to go instead – one place per area:

| Area | Sandboxed (`contributes.tabs[].on`) | Native (`slots`) |
|---|---|---|
| Web server, Databases, Minecraft, Projects, Mail, System, AI, Backups | `area:web` … `area:backups` | `web.tabs`, `dbs.tabs`, `minecraft.tabs`, `projects.tabs`, `mail.tabs`, `system.tabs`, `ai.tabs`, `backups.tabs` |
| Tasks (new) | `area:tasks` | `tasks.tabs` |
| Go live | `area:live` | `live.tabs` with `group` (`erreichbar`, `schuetzen`, `betrieb`) – the **same id** from several extensions shares one tab (e.g. `discord`) |
| Game servers (extension) | – | `games.tabs` – shown by "Game servers" through `useAreaTabs('games')` from `@hostwerk/kit` |
| Detail views | `contributes.sections` (section 21) | `sections` |

- `area:tasks` is new – a package using it needs `"hostwerk": ">=3.0.0"` (older checkers reject unknown areas).
  Native slots need no higher version: an older Hostwerk simply does not show them.
- **Sections with a role** – `"role": "motd"` on `mc.overview`: the section shows and edits how players see the server
  (MOTD and icon); Hostwerk's own card "How players see your server" then steps back, so there is only one preview.
  Native: `sections: { 'mc.overview': [{ id, role: 'motd', … }] }`.

**Also new in 3.2:**

- `Hostwerk.saveFile(name, text, type)` – save text as a file (CSV, Markdown, JSON …); the sandboxed frame cannot download
  itself. Text only (`text/*`, JSON, XML, YAML, SQL, SVG), at most 5 MB, a file name with extension, no executable
  extensions, one file per second. Returns `{ name }`.
- `GET /system/info` (`read:system`) – machine profile: operating system with build, processor, graphics card, drives,
  network adapters (addresses only), runtimes (Node, Java, Python), update state, last backup, health and installed
  extensions. Cached for 60 s (`?fresh=1` measures again). `GET /system/health` returns the health part.
- `GET /live/security` returns `titles: { de, en }` for every check (`title` stays German as before).

## 25. SDK 3.3: stable services instead of core internals, traces and an uninstall hook

Hostwerk 3.0 and newer (with SDK 3.3). Only additions. For own server code (`backend`, section 15).

### Stable services

Up to SDK 3.2, native extensions had to reach into Hostwerk's internals for some things (`ctx.ai.quick`,
`ctx.minecraft.readMeta`/`addonDir`, `ctx.patchUpdates`, `host.core('download').isOffline()`, the core's image code, writing
straight into `~/.ssh`). Now there are documented, versioned services on `host` – with permissions in the package:

| Service | Permission | Sandboxed | Returns |
|---|---|---|---|
| `host.ai.quick.ready()` · `.run(task, { text, lang, context })` | `use:ai` | yes | `task`: `translate`, `explain`, `summarize`, `describe` → `{ text, cached }`; at most 6000 characters, only when the AI assistant is on (409 otherwise) |
| `host.minecraft.addons(serverId?)` | `read:minecraft` | yes | plugins/mods `[{ file, name, version, enabled, kind }]` – without `serverId` one `{ server, addons }` per server; read only |
| `host.updates.pending()` | `read:updates` | yes | pending security updates `[{ key, component, label, current, latest }]` |
| `host.updates.apply(key)` | `change:updates` | no | installs a pending update – with trial run and fallback like *Settings → Updates*, noted in the activity log → `{ ok, skipped, error }` |
| `host.net.offline()` | – | yes | `true` when offline mode is on |
| `host.icons.favicon(url)` | `fetch:icons` | no | icon of a **public** website `{ mime, data }` or `null` – https only, never the home network or 127.0.0.1 (not via DNS or redirects either), at most 512 KB, cached for 30 days |
| `host.sshKeys.import({ name, privateKey, publicKey })` | `write:ssh-keys` | no | puts the key under a new name into `~/.ssh` (600/644) – never overwrites (409 `EXISTS`) |
| `host.images.list()` | `read:apps` | yes | Docker images with tag from Docker apps, Compose stacks and Docker game servers `[{ source, owner, name, image, repo, tag, digest }]`; read only |
| `host.traces.add/remove/list` | – | no | traces outside the own folder (below) |

**Mail programs** (permission `connect:mail`): mail servers are free to choose (Gmail, web.de, your own domain …) – a list
under `network` wouldn't work. With this permission server code may speak IMAP/SMTP/POP3 to any server the person enters
when setting up an account (ports 25, 110, 143, 465, 587, 993, 995, 2525). Sandboxed, `runner.js` enforces exactly these
ports and still blocks the home network and 127.0.0.1; websites (autoconfig too) only via `network`. Used by *E-mail accounts* (`mail-accounts`).

**Feature detection:** `host.sdkVersion` (e.g. `"3.3.0"`) and `host.supports('updates.apply')` – `true` means available
**and** allowed (permission in the package, sandboxed or not). The same release keeps running on older Hostwerk:

```js
const pending = host.supports && host.supports('updates.pending')
  ? await host.updates.pending()
  : (host.ctx.patchUpdates && host.ctx.patchUpdates.pending) || []; // fallback for Hostwerk before SDK 3.3
```

Sandboxed modules get the reading services (column "Sandboxed") – as promises, `host.supports()` too
(so `if (await host.supports('updates.pending'))`). Installing updates, icons from the internet,
SSH keys and traces exist only for official packages inside the Hostwerk process.

New permissions need `"hostwerk": ">=3.0.0"` and `"sdkVersion": "3.3"` – older checkers do not know them and reject the package.

**Deprecation:** the internals above stay as a fallback but are deprecated since SDK 3.3.0 (2026-10-22) and go away no earlier
than SDK 4.0.0 and not before 2027-10-22 (rules from section 19). The checker names the replacement as a hint (`internals`, no
deduction) as long as the code does not ask the stable service first.

### Traces outside the own folder

When the server code creates something outside its folder – a Windows task, a folder under `%ProgramData%`, a registry key,
a service, a firewall rule, a port forwarding – it reports it as a **trace**:

```js
host.traces.add({ kind: 'task', id: 'task', label: '\\Hostwerk\\DiskHealth', admin: true, remove: { name: '\\Hostwerk\\DiskHealth' } });
host.traces.add({ kind: 'dir', id: 'folder', label: 'C:\\ProgramData\\HostwerkDiskHealth', admin: true, remove: { path: 'C:\\ProgramData\\HostwerkDiskHealth' } });
// cleaned up itself (e.g. feature switched off):
host.traces.remove('task');
```

| `kind` | `remove` | Hostwerk removes it with |
|---|---|---|
| `task` | `{ name }` | `schtasks /Delete` (default: admin) |
| `file`, `dir` | `{ path }` (absolute) | delete; with `admin: true` through the admin prompt |
| `registry` | `{ key, value? }` – at least three levels below `HKCU`/`HKLM` | `reg delete` (HKLM = admin) |
| `service` | `{ name, user? }` | Windows `sc.exe delete`, Linux `systemctl (--user) disable --now` |
| `firewall` | `{ name }` | `netsh advfirewall firewall delete rule` (admin) |
| `port-forward` | `{ protocol, port, router? }` | only the extension itself (uninstall hook) – otherwise a hint stays |

Traces are **data, not commands**: how a trace is removed is decided by Hostwerk per kind. Paths may not be drives, user,
system or Hostwerk folders; characters like `" & | % ^ < >` are never allowed; at most 50 traces per extension.

Who sees them: the extension pop-up (puzzle sign) under "What it set up on your PC", the *Uninstall* step with a tick per
trace, maintenance (*Remove* with "Also remove what it set up on this PC") and *Remove Hostwerk* (entry "Traces of
extensions"). Everything that needs administrator rights is removed with **one** prompt. Unticked or failed traces stay
orphaned in the list – *Remove Hostwerk* offers them again.

The checker warns (`traces`) when the server code visibly creates tasks, registry entries, services or files under
`ProgramData` but never calls `host.traces.add()`.

### Uninstall hook

```js
exports.uninstall = async (host, { traces }) => { /* e.g. delete port forwardings in the router */ };
```

`uninstall()` runs **only when removing** – never when switching off, updating, in safe start or when quitting (that stays
`deactivate()`). Order: `uninstall(host, { traces })` (at most 60 s, sandboxed 30 s) → Hostwerk removes the ticked traces the
module did not deregister itself with `host.traces.remove(id)` → `deactivate()` → package gone. `traces` are the traces the
user ticked. Errors in the hook do not stop the removal. The extension's data stays as before.

**Also new in 3.3:** `ctx.games.summary()` (extension "Game servers" 1.10+) returns `version` (Steam build id where Steam
knows it) and `image` (Docker image with tag) per server – read only.

## 26. SDK 3.4: screens of their own and device sign-in

Hostwerk 3.0 and newer (with SDK 3.4). Only additions. For native extensions (`ui` and `backend`, section 15) – the official
extension “Hostwerk app” (`hostwerk-ext-pwa`) uses all of it.

### A screen of its own

```js
// ui/src/index.jsx
export default {
  screens: { handy: { Component: PhoneApp, mobileHome: true } },
};
```

The screen shows under `#/handy` without Hostwerk's sidebar – messages, jobs and dialogs stay. `mobileHome: true`: on small
screens (< 700 px) Hostwerk starts there instead of the overview. Routes Hostwerk uses itself (`#/web`, `#/ki` …) cannot be
taken; the route is a–z, 0–9 and `-`. Screens never land in “recently visited”.

### Buttons at remote access and more building blocks

Slot `live.remote.actions` – buttons in the head of Go live → Remote access (the component gets `remote`, the status). From
`@hostwerk/kit`: `stopAllGuarded()`, `confirmStopOne(svc, name)`, `runGate()` and `setStopGate(fn)` (Hostwerk's stop guard – `fn`
is an extra confirmation, e.g. the passkey, `null` removes it again), `askAi(question)`, `EmergencyButton`, `EmergencyBanner`,
`AiQuotaWidget`, `HwLogo`.

### Device sign-in (service `devices`)

Sign-in stays Hostwerk's (password + two-factor code, passkeys, lockout per address and per account). A native extension may add
one more credential by providing the service `devices`:

```js
host.provide('devices', {
  verify(req) { /* → { user, userId, role, device } or null – asked for every request without a session */ },
  logout(req) { /* sign-out on this device → Set-Cookie string that clears your cookie, or null */ },
  removeAll() { /* “Sign out everyone” under remote access */ },
});
```

What Hostwerk guarantees: `verify` is only asked when remote access is on and the request has no valid session; the result
runs through the same checks as a normal sign-in (Team & roles `allowed()`, filtered overview, emergency mode). Return the role
of the account **at that moment** – never one stored on the device. Check with `host.supports('devices')`.

Rules for your own credential (the checker cannot see them, the catalogue review does): store only hashes of secrets, cookie
`HttpOnly; Secure; SameSite`, refuse requests another site started (`Sec-Fetch-Site` other than `same-origin`/`none`), invalidate
on a password change, count wrong codes with `ctx.remote.fail(ip)`, end sessions with `ctx.remote.dropSessions(s => …)`.
